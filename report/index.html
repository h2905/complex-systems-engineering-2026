SYSTEM BOUNDARY

系统对象与边界

平台位于 Systems 层，向上接收运动意图，向下协调转向、制动、驱动与悬架。

→

→

→

范围内

运动意图解释、多执行器协同、冗余仲裁、状态估计、故障降级、统一接口与事件记录。

范围外

感知算法、全局路径规划、云端调度，以及单电机、制动卡钳等执行器机械本体设计。

边界原则

上层给出任务意图，平台必须说明当前能力；能力未知或不足时，不得默认继续正常执行。

平台的核心输出不是“某个执行器已在线”，而是“当前仍可完成什么运动，以及还能持续多久”。

系统层级 / 六层分析04
TRACEABILITY

一个左转任务如何向下传递

用同一场景检查六层之间的接口和责任，避免每层各写一套互不对应的需求。

任务

完成无人接驳

安全到达站点，不依赖车内驾驶员。

体系

批准 ODD 与任务

调度下发站点、路段、天气边界和救援条件。

整车

规划左转轨迹

选择 12–15 km/h、曲率和安全停车位置。

系统

分解运动指令

生成转角、制动、轮端扭矩和姿态目标。

子系统

执行器协同

跟踪角度、控制速度、抑制侧倾。

模块

状态反馈

回传角度、电流、温度、轮速和健康状态。

设计含义

任务层改变会向下传递约束；模块级能力不足也必须向上形成能力声明。缺少任何一层，需求链都会在集成或验证阶段断开。

课程示例参数

左转车轮转角约 +32.5°、目标车速约 12 km/h、整体状态 NORMAL。该组参数仅用于解释传递关系，不作为量产结论。

系统层级 / 场景传递05
CONOPS / OPSCON

运营概念与系统运行概念

ConOps 描述业务怎样运转，OpsCon 说明线控底盘平台在其中承担什么。

ConOps：城市 L4 出行服务

  • 运营公司组织车辆、云控、路侧、补能、维护与救援资源。
  • 车辆在批准的 ODD、车辆状态和任务边界内提供载客服务。
  • 每次行程、故障和维护数据回到运营决策与安全证据。

OpsCon：线控底盘平台

  • 输入：轨迹、速度、加速度、安全停车请求和整车状态。
  • 处理：意图解释、执行分配、协同、仲裁、降级和状态估计。
  • 输出：转角、制动力、轮端扭矩、姿态指令及剩余能力。
NORMAL全通道能力

执行常规任务

DEGRADED受限但可控

降低速度或任务范围

MRM最小风险机动

禁止新任务并安全停车

SAFE_STOP驻车与隔离

等待维修或救援

公共网络可以辅助运营，但本地运动控制、故障仲裁和 MRM 不能依赖云控链路。
需求定义 / 运营概念06
STAKEHOLDERS

相关方需要并不总和

需求定义不仅收集愿望，也要把安全、效率、成本和合规之间的冲突显式写出来。

相关方主要需要可能冲突处理方向
乘客安全、平顺、状态可理解。紧急制动与乘员舒适性。区分正常、紧急和 MRM 减速度包线。
运营方连续服务、成本可控。安全裕度与车辆可用率。风险分级、恢复流程和能力化调度。
云控与远程人员掌握真实能力与事件。远程效率与本地安全授权。本地安全逻辑优先，远程不得绕过锁存。
开发与安全团队稳定接口和完整证据。迭代速度与验证充分性。版本化接口、变更影响分析和回归。
监管与保险方记录完整、责任可追溯。证据范围与数据隐私。最小必要采集、分级保存和授权访问。
维修与供应商可隔离、可诊断、责任清晰。平台统一性与专有方案。接口控制文档、维护模式和隔离点。
其他道路参与者车辆行为可预测。运营效率与轨迹激进度。降级和 MRM 不超出可控车辆边界。
需求定义 / 相关方07
BRS / STRS

从业务目标到相关方需求

BRS 采用 BR-01 至 BR-10；StRS 采用 SR-01 至 SR-22。本次汇报只展示与后续安全场景直接相关的需求。

编号需求摘要通过准则
BR-01在定义 ODD 内完成无人化接驳，不依赖车内驾驶员完成常规行程。批准 ODD 内完成无人运行验证与运营审核。
BR-02避免底盘运动执行单点失效导致不可控运动。安全分析、故障注入与台架或实车证据闭环。
BR-04乘客获得可解释、与安全约束一致的运动体验。加速度、冲击与姿态满足舒适基线。
BR-07任务、故障、降级、维护与验证数据形成证据链。安全要求可追溯至场景、实现和测试。
SR-02持续发布可用、受限、MRM、隔离状态。整车与云控一致解析，状态迁移正确。
SR-08把轨迹和停车意图转换为相互约束的执行指令。场景验证无持续执行器冲突。
SR-09关键执行通道单点故障时检测、隔离并保持最低能力。满足降级包线或进入 MRM。
SR-10无法维持最低能力时进入并保持 MRM。MRM 可重复进入，驻车状态可确认。

VALIDATION SLICE

先限定一个可以验收的切片

SYSTEM UNDER STUDY

线控底盘平台

接收 AD 轨迹与速度意图，协调双转向通道、制动和驱动，并实时声明剩余能力。

FAULT TRIGGER

左前转向通道失能

执行器开路、反馈失效，或指令与实际角度持续不一致。机械本体设计不属于本切片。

ACCEPTANCE RESULT

降级可控或安全停车

不能悄悄回到 NORMAL；最终状态应为 DEGRADED、MRM 或 SAFE_STOP。

初始条件课程验证基线说明
道路干沥青，左转半径约 15 m后续需按整车动力学和试验道路确认。
车辆半载，车速 15 km/h用于建立单故障切片的初始参数。
时间目标检测约 50 ms，接管约 100 ms作为待验证指标，不构成量产承诺。

CONTROL STRUCTURE

控制结构与状态迁移

AD 域负责运动意图；平台负责可实现性、仲裁和降级；执行器与车辆状态回到平台形成闭环。

COMMAND

曲率、目标速度、加速度上限、安全停车请求。

HEALTH

独立健康判断

指令、角度、电流、温度和通信新鲜度。

AUTHORITY

锁存式仲裁

决定模式，阻止未知状态回到 NORMAL。

EXECUTION

双通道转向

A 主执行，B 热备；制动和驱动受同一模式约束。

FEEDBACK

转角、横摆、轮速、剩余能力和事件序号。

S0 · NORMAL双通道有效

正常转向与速度请求

S1 · DEGRADED单通道有效

B 接管，限速并声明能力

S2 · MRM无有效转向

S3 · SAFE_STOP驻车与隔离

系统需求 / 控制结构11
SYSTEM REQUIREMENTS

系统需求规格：只写可实现、可验证的内容

SyRS 以 FR、PR、DR 编号，并直接追溯到相关方需求和 STPA 安全约束。

编号需求陈述初始验收方向
FR-01同时监测双通道指令、实际角度、电流、使能和通信新鲜度，区分有效、降级、未知和故障。两类以上独立证据不一致时不得保持有效。
FR-02主通道失效时锁存故障、阻断错误指令，并切换至已通过自检的热备通道。故障后不自动返回 NORMAL。
FR-03切换时保持转角和横摆趋势连续，禁止阶跃式转向修正。控制周期 10 ms；不得触发驱动扭矩增加。
FR-04仅一个有效转向通道时进入 DEGRADED，限速并声明可实现能力。初版速度上限 20 km/h，待整车标定。
FR-05无有效转向通道时拒绝新任务、进入 MRM，并协调制动、驱动与驻车。初版 100 ms 内发出 MRM，减速度不超过 0.3 g。
PR-01/02健康判断、仲裁和转角更新周期固定；故障检测时间受控。周期 10 ms；检测目标不超过 50 ms。
PR-03热备通道在明确时序内接管并保持指令连续。接管目标不超过 100 ms。
DR-01记录故障码、状态迁移、双通道反馈、指令序列与统一时间戳。一次测试可由事件序列独立重建。
系统需求 / SyRS12
INITIAL ARCHITECTURE

架构重点是把故障隔离路径画出来

双通道不是把同一套资源复制两份；供电、通信、计算、时间源和机械依赖都要检查共因故障。

A / B

主通道与热备通道

两通道持续自检，热备输出受控；只有在仲裁器授权后才接管执行权。

H

独立健康判断

同时比较指令、实际转角、电流、温度、时间戳和车辆横摆响应。

M

锁存式模式仲裁

故障或未知状态不得回到 NORMAL，恢复必须经过维修确认和重新自检。

R / E

MRM 与证据记录

无有效转向时禁止增扭、受控停车；完整保存模式迁移、反馈和版本。

“未知即不安全”：健康状态不能确认时，不授予正常执行权。
安全架构 / 初始架构13
STPA

从危险反推不安全控制动作

本次分析聚焦错误过程模型、反馈失效和接管动作本身带来的风险。

危险不安全控制动作因果场景安全约束
H-01 无法维持预期路径UCA-01 健康未知时仍发布 NORMAL通信在线被误认为执行器可用；反馈陈旧。SC-01 未知状态不授权 NORMAL。
H-01 无法维持预期路径UCA-02 备份未完成自检即接管方向或零位错误，切换成为新风险。SC-02 接管前完成自检和授权。
H-02 非预期横摆UCA-03 接管时未限扭矩就输出大转角力矩冲突、积分饱和或指令阶跃。SC-03 限扭矩、限变化率并保持闭环。
H-01 失去方向控制UCA-04 无有效转向时继续驱动停车距离和横向裕度持续缩小。SC-04 禁止增扭并进入 MRM。
H-02 收敛不可预测UCA-05 确认失效后延迟请求 MRM等待更优决策导致停车窗口缩短。SC-05 固定超时并及时安全停车。
安全需求落实内容
SAF-01 / 02未知状态不得进入 NORMAL；故障必须锁存，未经维修确认不得自动恢复。
SAF-03双通道不共享单一电源、通信路径或时间源，共性故障必须可检测。
SAF-04 / 06无转向能力时禁止增扭并进入 MRM；接管期间限制扭矩和转角变化率。
安全分析 / STPA14
VERIFICATION

用故障注入证明系统行为

每个用例同时检查模式迁移、时序、车辆运动和证据记录，而不只看是否“报警”。

用例注入条件通过证据
VT-0115 km/h 定曲率左转中切断 A 通道使能，B 通道热备。检测和接管满足基线；不返回 NORMAL；无驱动增扭。
VT-02保持旧角度值但停止更新时间戳，并制造指令与实际角度不一致。判为未知；禁止 NORMAL；保存完整故障快照。
VT-03A 通道失效，同时 B 通道自检失败或供电中断。及时请求 MRM；禁止驱动增扭；完成受控减速与驻车。
VT-04断开共享通信或时钟；清除故障码但不维修。共性故障可检测；故障锁存；维修确认后才允许重新自检。

试验顺序

模型在环 → 故障注入台架 → 封闭场地低速左转 → 按结果调整速度、转角与减速度边界。

未闭合项

机械共因、轮胎与载荷影响、时钟同步精度、MRM 停车位置和乘员冲击仍需实车数据。

SCENARIO LAYERS

场景分五层展开

从运营环境逐层收敛到模块状态。上层决定任务是否成立，下层决定任务能否执行。

S0 / OPERATIONS

运营与体系

任务、ODD、调度、云控、远程协助、救援、监管与维护。

S1 / ENVIRONMENT

道路与环境

交叉口、车道、坡度、附着、天气、光照、视野和交通参与者。

S2 / MISSION

车辆任务

路线、左转动作、目标速度、加速度、载荷、乘员与停车位置。

S3 / SYSTEM

底盘平台

模式、执行指令、健康状态、剩余能力、时延与时间戳。

S4 / MODULE

执行与模块

双转向通道、制动器、驱动、悬架、传感器、电源与通信。

向下传递

任务选择道路与轨迹；平台把轨迹转换为运动能力；模块故障反过来限制上层任务。

向上约束

ODD 或模块能力不满足时，平台不能只报故障，还要声明还剩多少转向、制动和速度能力。

场景设计 / 分层16
SCENE ELEMENTS

每一层需要记录的要素

要素选择围绕“可能改变运动任务、能力或安全边界”的信息，避免把场景写成完整环境数据库。

层次核心要素本阶段关注点
S0 运营与体系接驳任务、站点、批准 ODD、调度策略、远程人员、救援与监管。车辆是否被允许进入此任务，异常后由谁接收事件。
S1 道路与环境交叉口类型、车道宽度、坡度、附着、天气、光照、行人与非机动车、对向直行。环境是否仍在 ODD 内，可见性和附着是否改变运动边界。
S2 车辆任务轨迹、曲率、目标速度、加速度、载荷、乘员状态和安全停车位置。任务需要多少时间、空间和执行能力。
S3 底盘平台模式、输入请求、四类执行指令、健康状态、剩余能力、时延和日志。系统能否实现任务，何时应限速、降级或 MRM。
S4 执行与模块转向双通道、制动、驱动、悬架、角度、电流、温度、压力、轮速、电源和通信。模块状态是否足以支撑平台声明的最低能力。
场景设计 / 要素17
OPERATING DESIGN DOMAIN

正常运行设计条件：运行设计范围

下列条件构成课程阶段的正常 ODD。超出范围时，平台应收紧授权或停止任务。

类别正常条件超出条件时
道路批准的城市低速道路；信号或标志明确；车道宽 ≥ 3.25 m；坡度 ≤ 5%；左转半径 > 10 m；标线可识别。未批准路段、几何或路权不确定时拒绝任务。
交通混合交通；存在机动车、行人和非机动车，但其行为能在预测窗口内识别。高密度冲突、道路封闭或无法解释的交通行为触发减速或停车。
速度常规 ≤ 30 km/h；典型左转 12–15 km/h；最终阈值按车型、载荷和附着标定。超出能力声明时不得继续推进任务。
天气与光照道路附着良好；无积水或积雪；白天或满足照明要求的夜间。雨雪、大雾、积水、低附着或强逆光时收紧 ODD。
通信云控可辅助运营，但本地控制、仲裁和 MRM 不依赖公共网络。通信中断时保持本地能力，完成安全动作或停车。
能量与热高压、低压、驱动、制动与控制器温度处于供应商声明范围。热降额、能量不足或制动能力下降时更新剩余能力。
运行条件 / ODD18
SYSTEM AND PEOPLE

运行设计条件：系统状态与人员状态

车辆自检、能力声明和人员职责必须同时满足条件，正常任务才成立。

系统状态

主状态NORMAL，无锁存故障，无未确认健康状态。
自检双转向、制动、驱动、悬架、传感器、电源与通信通过。
一致性指令、反馈和车辆响应在允许误差内；时间戳新鲜且单调。
能力声明给出可用转角、速度上限、制动能力、模式原因和有效时间。
时间基准AD 请求、平台控制、执行反馈与事件记录可核对。

人员状态

车内人员正式运营不配驾驶员；乘客坐稳并系安全带；车门关闭。
试验安全员初始道路验证阶段可随车，并可使用独立急停。
远程人员经过培训，能读取状态、原因和处置项；同时监控车辆数须验证。
授权边界远程建议不得绕过本地安全约束、故障锁存和 MRM。
运维与救援具备隔离、断电、拖移权限，并知道如何读取危险状态。
正常运行的判据是“条件满足且能力已声明”，并非车辆已经上电或某个执行器在线。

CONCLUSION

结论

本报告形成一条连续的系统设计与运行分析主线，并明确当前可以确认和仍待验证的内容。

系统工程主线

从任务与体系出发确定平台边界，再通过 BRS、StRS、SyRS 和安全架构把目标变成可实现、可验证的要求。

安全设计重点

未知状态不授权正常执行；故障要锁存；备份接管要保持指令连续；无法维持最低能力时进入 MRM。

场景分析重点

正常任务必须同时满足 ODD、系统健康和人员职责条件。风险来自场景偏差、能力更新滞后和错误状态。
